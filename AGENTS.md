# AGENTS.md

Руководство для агентных код-ассистентов, работающих в `s1app`.
Проверено по состоянию на 2026-03-04.

## Обзор проекта

- Стек: Perl-бэкенд (`Mojolicious::Lite`), статический фронтенд (`frontend/index.html`), PostgreSQL.
- Точка входа API: `backend/s1-api.pl`.
- Локальный запуск для разработки: `backend/start` (`morbo` на `127.0.0.1:3000`).
- Production-раннер: `hypnotoad` (см. `backend/s1-api.service`).
- В nginx заложены префиксы: `/s1/api/` -> backend и `/s1/` -> frontend (`nginx/s1.conf`).
- В репозитории сейчас нет CI, конфигов линтера и коммитнутых автотестов.

## Ключевые файлы

- `backend/s1-api.pl` - маршруты API, загрузка конфига, глобальный хук обработки ошибок.
- `backend/s1-api.conf.dist` - пример runtime-конфига.
- `backend/init.sql` - минимальная инициализация прав/роли в БД.
- `backend/start` - команда локального dev-запуска.
- `frontend/index.html` - UI карты и интеграция поиска.
- `nginx/s1.conf` - правила проксирования и статики.
- `README.md` - описание API и предметной области (на русском).

## Build / Run / Lint / Test

Все команды выполнять из корня репозитория, если не сказано иное.

### Установка зависимостей (вручную)

- `cpanfile` отсутствует; Perl-модули ставятся вручную, например:
  - `cpanm Mojolicious Mojo::Pg Config::Simple DDP`

### Команды запуска бэкенда

- Проверка синтаксиса: `perl -c backend/s1-api.pl`
- Dev-запуск (скрипт): `sh backend/start`
- Dev-запуск (напрямую): `MOJO_MODE=development MOJO_LOG_LEVEL=debug morbo backend/s1-api.pl -l http://127.0.0.1:3000`
- Запуск в production-подобном режиме: `hypnotoad -f backend/s1-api.pl`
- Перезагрузка `hypnotoad`: `hypnotoad backend/s1-api.pl`

### Команды запуска фронтенда

- Пример простого статического сервера: `python3 -m http.server 8080 --directory frontend`
- Фронтенд вызывает `/s1/api/search`; для реалистичного поведения используй nginx-маршрутизацию из `nginx/s1.conf`.

### Линтинг и форматирование

- Обязательная минимальная проверка после правок бэкенда: `perl -c backend/s1-api.pl`
- Проверка фронтенда: открыть страницу и убедиться в отсутствии JS-ошибок в консоли браузера.
- Опционально (если установлено локально):
  - `perlcritic backend/s1-api.pl`
  - `perltidy -b backend/s1-api.pl`

### Тесты

- Текущее состояние: в репозитории нет коммитнутых `t/*.t`.
- Если добавлены Perl-тесты, использовать:
  - Все тесты: `prove -lv t`
  - Один файл теста: `prove -lv t/api/search.t`
  - Один тест-кейс: `prove -lv t/api/search.t --match "returns 400 on short q"`
- Smoke-проверки API без тестового набора:
  - `curl -i http://127.0.0.1:3000/api/ping`
  - `curl -i "http://127.0.0.1:3000/api/search?q=moscow"`

## Конфигурация

- Путь к конфигу по умолчанию: `backend/s1-api.conf` (в `.gitignore`).
- Кастомный конфиг: `perl backend/s1-api.pl --config /path/to/s1-api.conf`
- Разделы в `backend/s1-api.conf.dist`:
  - `[app]` (например, `log2file`)
  - `[db]` (`url_*`, `poll`)
  - `[hypnotoad]` (`listen`, `workers` и т.д.)
- Не коммитить реальные пароли, токены и локальные секреты.

## Правила стиля кода

Делай небольшие и локальные изменения; избегай широких рефакторингов без явного запроса.

### Perl-бэкенд

- Для новых Perl-файлов сохранять прагмы вверху: `use strict; use warnings; use utf8;`
- Следовать существующему стилю Mojolicious с сигнатурами (`Mojolicious::Lite -signatures`).
- Для обработчиков маршрутов предпочитать `sub ($c) { ... }`.
- Порядок импортов: прагмы/ядро -> Perl-модули -> Mojo/Mojolicious-модули.
- Удалять неиспользуемые импорты в изменяемом файле.
- Отступы: 2 пробела в блоках (как в текущем коде).
- Длинные `render(...)` и SQL-выражения переносить на несколько строк.
- Точки с запятой ставить последовательно во всех выражениях.
- Именование: API-роуты в lowercase, переменные короткие, но понятные (`$q`, `$qlen`, `$rows`).

### Типы и структуры данных

- Статической типизации нет; JSON-контракты считать строгими.
- Формат ошибок API сохранять стабильным: JSON-объект с ключом `error`.
- Не ломать текущую структуру ответов `/api/search` без отдельного запроса.

### Обработка ошибок и логирование

- Сохранять поведение глобального `around_dispatch`-перехвата, если специально не меняется политика ошибок API.
- На ошибки возвращать явный HTTP-статус + JSON с описанием.
- Валидацию входных параметров делать как можно раньше (fail-fast, 4xx).
- Неожиданные исключения логировать через `$c->app->log->error(...)`.

### База данных и SQL

- Использовать только параметризованные запросы; не интерполировать ввод пользователя в SQL.
- Фиксировать неочевидные SQL-допущения рядом с кодом.
- Учитывать текущее несоответствие: есть helper `pg`, но `/api/search` обращается к `$dbh`.
- При миграции слоя доступа к БД сохранять единообразие в пределах изменяемого потока.

### Фронтенд

- Сохранять подход без дополнительных зависимостей, если нет отдельной задачи на это.
- Использовать `const`/`let`, не использовать `var`.
- Именовать `id`/классы ясно и по назначению.
- Ошибки async-операций показывать пользователю и писать в консоль.
- Не ломать deployment-модель с префиксом `/s1` жестко заданными API-путями.

## Ожидаемый рабочий процесс агента

- Перед правками читать связанные файлы целиком (backend/frontend/nginx по контексту).
- После правок бэкенда запускать `perl -c backend/s1-api.pl`.
- После правок фронтенда проверять страницу и консоль браузера.
- При добавлении тестов включать в отчет минимум одну команду запуска одного теста.
- Держать коммиты тематическими; не смешивать несвязанные изменения.
